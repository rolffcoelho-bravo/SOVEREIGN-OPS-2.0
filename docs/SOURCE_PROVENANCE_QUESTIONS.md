# Source provenance questions for the filtered release

The versioned filtered release is useful for research only after its source
clock, row-selection, and failure semantics can be reconstructed. These
questions are a concrete request for a transformation manifest or author
clarification. They do not assume the published notebook generated the Excel
package unchanged.

1. **Clock conversion:** What timezone and offset did each original SCADA and
   failure workbook use? Which code converted source timestamps to the v2 `Z`
   strings? Did the conversion localize naive datetimes before UTC conversion,
   and which IANA zone and daylight-saving ambiguity policy were used?
2. **Repeated hour:** For each turbine, why do both filtered views contain
   conflicting 02:00–02:50 `Z`-marked rows on 30 October 2016 and 29 October
   2017? Can source row identifiers or original offsets map each member of a
   repeated pair to a unique instant? Until then, no row-order assignment or
   deduplication is justified.
3. **Filtering recipe:** Are the `_F95` and `_F99` workbook names generated by
   the tagged public notebook, another revision, or a separate pipeline?
   Provide the exact commit, configuration per turbine and year, selected
   confidence setting, negative-power policy, cluster count, random seed,
   distance threshold, and workbook export step. The release description says
   99.9%, while the paper and tagged code say 99%.
4. **Fit boundary:** Were K-Means centers, covariances, and any other filtering
   statistics fitted on the entire 2016–2017 period or on a training period
   ending before each evaluation interval? Provide fit-period boundaries and
   row selection indices. Full-period fitting would threaten prospective
   inference even if the later detector used chronological splits.
5. **Row lineage:** How many raw source rows entered each asset/year, how many
   were dropped at each preprocessing stage, and why? The paper describes
   417,093 samples in its study; the verified v2 F95 view has 211,465 rows
   over 2016–2017. Those are not an established common population, so a
   retention percentage cannot be inferred by dividing them.
   The [versioned access audit](EDP_VERSION_ACCESS_AUDIT.md) found that the
   version 1 public API root-level listing currently exposes only two PNGs
   despite its eight-file description; other folders were not enumerated.
   Please provide source-authoritative raw workbook identities and hashes or a
   working versioned download route.
6. **Failure meaning:** Does each logged timestamp denote detection, physical
   onset, repair entry, or another operator action? What is its clock? How are
   repeat faults and a recovery interval identified? The paper treats the two
   T07 generator records on 20–21 August 2017 as consecutive faults; their
   independence is not established. Why does the paper report 27 failures
   while the v2 workbook has 28 rows, including seven T09 rows without SCADA?
7. **Rights and reproducibility:** Which original source file/version and
   licence apply to each derivative workbook? Is redistribution of derived
   row-level data authorized? Provide file hashes, code revision, settings,
   input/output counts, and generated-time metadata without publishing raw
   operational content in this repository.

An acceptable answer is a source-linked, versioned transformation record. If
some details cannot be recovered, record that uncertainty, keep affected
events in `UNDETERMINED`, and restrict claims to scenario-specific descriptive
analysis. Do not select an exposure cutoff or model benchmark from outcomes
before these source questions are addressed.
